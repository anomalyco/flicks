# Build a Plex replacement on tuned iroh

The fastest stack has five parts. The first is a single Rust binary per home server that speaks **iroh 1.x (QUIC over noq), tuned with large windows and BBR**, and embeds its own relay. The second is **direct play of the original file over byte ranges** as the default path, with in-process, keyframe-aligned fMP4 HLS remux as the first fallback. The third is a **pinned jellyfin-ffmpeg subprocess placed on whichever household GPU has headroom** for the transcodes that remain. The fourth is SQLite plus a Navidrome-style folder-hash scanner for the library. The fifth splits Deadbolt's sync model into three streams: membership, catalog and watch progress. Each layer fixes a specific Plex failure. There is no account server, because identity is Deadbolt's signed membership log plus QR pairing. Remote playback has no paywall and no throttled vendor relay, because every home server can relay at full speed. Servers stop being islands because each one replicates its catalog to the others. Transcoding is placed per session across all machines in the house. The biggest speed risks sit in places people don't expect. Stock iroh reached only about a third of a 110 MB/s LAN in public tests. Plex's and Jellyfin's slow starts come from session orchestration, not from remux CPU: remuxing the first segment takes under 50 ms. Watch progress ticks would swamp an unpruned causal log. Most of the "nice" features (trickplay, skip intro, loudness, credits detection) cost under one CPU-minute per hour of video if they share one read of the file. Reusing the Jellyfin 12 client ecosystem gets Infuse, Swiftfin and the TV apps on day one. Only a native client gets the peer-to-peer mesh.

## Six Plex failures map onto six design choices

Plex's 2025–2026 changes set the bar. Since **29 April 2025**, remote playback of personal video needs Plex Pass or a **$1.99/month Remote Watch Pass** ([Plex Support](https://support.plex.tv/articles/requirements-for-remote-playback-of-personal-media/)). A lifetime pass rose to **$749.99 on 1 July 2026** ([Plex blog](https://www.plex.tv/blog/new-lifetime-plex-pass-pricing/)). Credits skipping needs Plex Pass on both the admin's and the viewer's account ([Plex Support](https://support.plex.tv/articles/credits-detection/)). Watch Together was removed from the new apps ([Android Authority](https://www.androidauthority.com/plex-watch-together-removed-3529939/)). The users who moved to Jellyfin reacted mostly to removals and paywalls, not to missing features. The distributed design answers each grievance with a structural choice rather than a policy promise.

| Layer | Fastest choice | Key number behind it | Plex problem fixed |
|---|---|---|---|
| Transport | iroh 1.x, windows 16–32 MiB stream / 64 MiB connection, BBR, 2–4 parallel range streams, embedded iroh-relay on every server | 37 → 48 MB/s single-stream on a 110 MB/s LAN after tuning; CUBIC was 1.3–1.7 MB/s on pre-fix noq | 2 Mbps relay, account-mediated connections |
| Delivery | Direct byte-range play; else stateless in-process fMP4 HLS from a scan-time keyframe index; one-round-trip `/play` | First remuxed segment in 44–48 ms locally; Jellyfin users report starts of 12 s to 3 min | Slow starts, server CPU |
| Transcoding | Pinned jellyfin-ffmpeg subprocess, argv compiled from capability profiles, whole session on the best household GPU | Iris Xe: 3 × 4K60 HDR→1080p SDR; M1: 3 × 4K24 DV; GeForce capped at 12 sessions per host | Single-machine transcoding |
| Library | notify events + folder-hash rescans, in-process MKV/MP4 header parse, OSHash identity, SQLite WAL with one writer | MKV Cues for 20 min of video is 13 KB and reads in 0.28 ms; ffprobe costs ~100 ms per file | Bloat, slow scans |
| State sync | Membership log (unchanged), single-writer catalog feed + negentropy fallback, LWW progress registers with checkpoints | ~3 round trips for 1M items; 10–25× fewer progress ops | Servers as islands, cloud dependency |
| Clients | Jellyfin 12 API facade for third-party apps; native client (Rust core + AVPlayer/ExoPlayer, mpv fallback) for the mesh | Ferrofin: 0.64 ms direct-play first byte vs 4.12 ms in Jellyfin | Cloud login, app redesign churn |
| Features | One fused analysis pass per file; results keyed by content hash and shared between peers | Trickplay ~9 CPU-s/hour keyframe-only; R128 ~4 CPU-s/hour | Paywalled skip intro, 10–50 MB BIF per item |

The rest of this report justifies each row, layer by layer, and ends with a build order.

## Tuned iroh carries everything, but stock settings reach a third of the link

Deadbolt's network layer already uses `iroh = "1.3.0"` with a minimal endpoint preset and **no custom transport config** ([deadbolt net/Cargo.toml](~/dev/deadbolt/crates/net/Cargo.toml); [node.rs](~/dev/deadbolt/crates/net/src/node.rs)). That runs stock QUIC flow-control windows and the default congestion controller, which is fine for password entries and wrong for video. The best public real-hardware measurement is iroh issue #4286 (May 2026: two Apple-silicon Macs, Wi-Fi 6 to 2.5 GbE, iperf3 baseline ~110 MB/s). Vanilla config gave **37 MB/s**. BBR gave 42.65 MB/s, and BBR with a 32 MiB stream window and a 64 MiB send window gave **48.16 MB/s, about 45% of line rate**. CUBIC gave **1.3–1.7 MB/s**, roughly 30× slower, stalling for seconds after every 32 MB window ([iroh#4286](https://github.com/n0-computer/iroh/issues/4286)). Part of that collapse was a noq bug: BBR3 never received `on_packet_sent`. The fix took a benchmark "from 1.3 to 55 MiB/s" and was merged around 3 June 2026 ([noq#657](https://github.com/n0-computer/noq/pull/657)), probably before iroh 1.0 shipped mid-June ([TechTimes](https://www.techtimes.com/articles/318490/20260616/peer-peer-library-iroh-10-ships-dial-devices-key-not-ip-address.htm)). That should be checked against the noq version iroh 1.3 pins. n0 maintainers say Linux GSO/GRO is "consistently much faster" than macOS for saturating a link ([iroh#4286](https://github.com/n0-computer/iroh/issues/4286)).

The concrete tuning comes from these sources. Size windows to at least the bandwidth-delay product, as iroh's docs require ([docs.rs QuicTransportConfigBuilder](https://docs.rs/iroh/latest/iroh/endpoint/struct.QuicTransportConfigBuilder.html)). A mid-2026 writeup used **16 MiB per stream and 64 MiB per connection and send**, which covers the ~6 MiB BDP of a 100 ms × 500 Mbit link ([kith throughput.md](https://github.com/muhamadjawdatsalemalakoum/kith/blob/main/docs/throughput.md)). Use BBR through noq's `ControllerFactory`; this currently means pinning `noq_proto` because iroh exposes no stable BBR config. Split large reads into **2–4 parallel range streams** on one connection: on loopback that took one transfer from 77 to 93 MB/s ([kith](https://github.com/muhamadjawdatsalemalakoum/kith/blob/main/docs/throughput.md)). Run servers on Linux. Sustained video rarely needs the full link: a heavy 4K remux at 70 Mbit/s is under 9 MB/s ([jellyfin#15237](https://github.com/jellyfin/jellyfin/issues/15237)). Raw throughput still matters for seek refills, prefetch bursts, several clients per server and WAN paths. Untuned windows turn those into multi-second stalls.

The relay is where Plex's remote experience actually breaks, and where this design can win outright. n0 reports that about 9 in 10 iroh connections go direct ([iroh FAQ](https://docs.iroh.computer/about/faq)). The only large independent study, of libp2p hole punching, measured **70% ± 7.1%** across 4.4M attempts ([arXiv 2510.27500](https://arxiv.org/html/2510.27500v1)). Plan for 10–30% of remote pairs being relay-only. Those relays are slow. n0's paid Shared Relays cap at **5 MB/s** (40 Mbit/s) ([iroh Shared Relays](https://docs.iroh.computer/iroh-services/relays/shared)), and its public relays are throttled and for testing only. Tailscale's numbers show the gap clearly: in a 2026 test, DERP sustained **2.2 Mbit/s** while a home "peer relay" carried **27.5 Mbit/s** on the same path, 12.5× more ([Tailscale blog](https://tailscale.com/blog/peer-relays-international-networks)). The answer is to **embed `iroh-relay` in every home server** that has a forwardable port or UPnP. Configure clients with `RelayMode::Custom` and raise the per-client token bucket (`Limits::client_rx`) ([iroh self-hosted relays](https://docs.iroh.computer/iroh-services/relays/self-hosted); [rate limiting](https://docs.iroh.computer/relays/rate-limiting)). For households where no server is reachable, an optional cheap VPS relay does the same job. The relay sees only end-to-end encrypted QUIC. iroh's relay path runs over TCP/WebSocket, which adds head-of-line blocking. A QUIC relay transport is requested but not merged ([iroh#4395](https://github.com/n0-computer/iroh/issues/4395)).

Kernel TCP still beats userspace QUIC on bytes per CPU. A WWW'24 study found QUIC/HTTP3 delivers **up to 45% less throughput** than TCP/TLS/HTTP2 on lightweight clients above ~600 Mbps ([Zhang et al.](https://arxiv.org/pdf/2310.09423)). Quinn, noq's ancestor, was single-core bound in a 10 GbE testbed ([König et al., KIT](https://publikationen.bibliothek.kit.edu/1000161904/152028985)). That justifies one optional fast path: when client and server share a LAN, serve the same range protocol over **HTTP/1.1 or HTTP/2 on kernel TCP with TLS bound to the server's iroh key**. Keep iroh for discovery, authentication and everything off-LAN. Tailscale/Headscale has the better-proven data plane (13 Gbit/s single-stream with UDP offload, [Tailscale](https://tailscale.com/blog/more-throughput)), but it brings back a control server. libp2p has no relay fit for bulk traffic. Browsers can't hole-punch: iroh in wasm is **relay-only** ([iroh wasm docs](https://docs.iroh.computer/languages/wasm-browser)). Web clients therefore get HTTPS range requests to a reachable server, or WebTransport with `serverCertificateHashes`.

Seek latency on a warm connection is roughly one RTT plus a disk read: about 40–60 ms at 30 ms RTT. Cold connection setup costs 2 RTTs for QUIC and 3 for TCP+TLS 1.3 ([QUIC deep dive](https://iotdigitaltwinplm.com/quic-http3-protocol-deep-dive-handshake-streams-loss-recovery-congestion-control-2026)). iroh connections start on the relay and upgrade to direct ([iroh on QUIC Multipath](https://www.iroh.computer/blog/iroh-on-QUIC-multipath)), so clients should **pre-dial every known server at launch** and keep one long-lived connection per server. No published measurement of iroh's relay-to-direct upgrade time or its time-to-first-byte exists. Both should be measured in the first slice.

## Direct play by byte range beats every server pipeline by seconds

Media servers aren't slow at starting playback because of CPU. A local benchmark for this research (Apple M5 Max, FFmpeg 9.0.2, warm cache, 1.23 GB 20-minute 1080p MKV) measured the steps directly. Spawning ffmpeg took **27 ms**. A stream-copy remux to fMP4 HLS had its first 6 s segment listed after **44–48 ms**, even after a mid-file seek. The whole file remuxed in **0.94 s** (~1.3 GB/s). Users meanwhile report Jellyfin starts and scrubs of "12s -> 3 minutes" even when direct streaming ([Jellyfin forum](https://forum.jellyfin.org/t-solved-tracking-starting-slow)), and Plex transcode starts of 10–45 s ([AVS Forum](https://www.avsforum.com/threads/plex-slow-to-start-playback.3293824)). The delay comes from orchestration. Jellyfin restarts ffmpeg on seeks outside the produced range ([Jellyfin forum](https://forum.jellyfin.org/t-how-does-jellyfin-live-transcoding)). It ran ffmpeg twice on resume ([jellyfin#11025](https://github.com/jellyfin/jellyfin/issues/11025)). It has had playlist/segment mismatches that stall native HLS clients ([PR #16341](https://github.com/jellyfin/jellyfin/pull/16341)). Plex waits up to a 20 s `SegmentedTranscoderTimeout` ([WebTools-NG](https://github.com/WebTools-NG/WebTools-NG/wiki/transcoder)). Both need 3–5 sequential requests before the first media byte. The clients users rate best, Infuse and Kodi, skip all of that and range-read the original file ([Firecore community](https://community.firecore.com/t/support-jellyfin-remote-access-limits/53047)).

The delivery ladder therefore has three rungs:

1. **Direct play** of the original bytes, for any client that can demux the container (mpv, Kodi, Infuse, ExoPlayer, Chromium with MKV). This costs zero server CPU. A seek is one range request.
2. **Stateless, keyframe-aligned CMAF/fMP4 HLS remuxed in-process**, for AVPlayer and Safari, which can't open MKV ([Swiftfin players.md](https://github.com/jellyfin/Swiftfin/blob/main/Documentation/players.md)). Segment N is computed from the stored keyframe index, so no per-session process exists and a seek is just a different segment number. Use fMP4 rather than TS: TS adds **5–15%** overhead ([Dolby OptiView](https://optiview.dolby.com/resources/blog/streaming/low-latency-chunked-cmaf)) and can't carry HEVC in HLS ([5centsCDN](https://www.5centscdn.net/blog/mpeg-ts-vs-fmp4)). Aim for ~4 s segments with 2 s opening segments, cut at source keyframes. That lets ExoPlayer reach its **2.5 s start buffer** with one small download ([ExoPlayer DefaultLoadControl](https://github.com/google/ExoPlayer/blob/release-v2/library/core/src/main/java/com/google/android/exoplayer2/DefaultLoadControl.java)). nginx-vod-module is the production precedent for variable segment lengths ([README](https://github.com/kaltura/nginx-vod-module/)). LL-HLS adds nothing for VOD.
3. **Transcode**, only when the codec is unplayable (next section).

Make the API one round trip. `GET /play/{item}?t=resume` returns the decision plus either the direct URL with the byte ranges of the header, index and resume cluster, or an inline media playlist with a pre-generated init segment and the segment index for `t`. It should run no probe, no bitrate test and no process. A Swiftfin slow-start case was partly a pre-play "Auto Bitrate Test" ([Swiftfin#1444](https://github.com/jellyfin/Swiftfin/issues/1444)). In a distributed household the response names the node that holds the file, so bytes never route through a coordinator. The Rust reimplementation Ferrofin shows the ceiling for this kind of work: **0.64 ms direct-play first byte vs 4.12 ms** for Jellyfin 12.2, and **184 ms vs 431 ms** to the first HLS segment ([Ferrofin](https://github.com/mangoleaf/ferrofin)).

Rust has no mature drop-in MKV-to-fMP4 remuxer, but the pieces exist. `matroska-demuxer` covers only the WebM-compatible subset ([crates.io](https://crates.io/crates/matroska-demuxer)). `muxide` writes fMP4 for HLS/DASH from explicit PTS/DTS ([docs.rs](https://docs.rs/muxide/0.2.0/aarch64-unknown-linux-gnu/muxide)). Write a small custom EBML cluster reader, copy `avcC`/`hvcC` into the init segment, and keep ffmpeg (spawned, or via `ffmpeg-next` 9.0, which is in maintenance mode but builds against FFmpeg 9 ([crates.io](https://crates.io/crates/ffmpeg-next))) for exotic containers and audio transcodes.

Multi-source fetching is a separate question from playback. iroh-blobs verifies BLAKE3 in **16 KiB chunk groups**, catches a bad provider within 16 KiB ([iroh blog](https://www.iroh.computer/blog/blob-store-design-challenges)), and keeps an outboard of about 0.4% of the file. On loopback, though, bao verification was the CPU bottleneck. Building outboards for a 50 TB library would add ~195 GB. Within one household, the authenticated QUIC connection already guarantees integrity from a trusted server. So stream playback as plain ranges over a custom iroh ALPN, and use iroh-blobs only for replicating files, offline downloads and fetching from several servers that hold the same file. In that multi-source case, follow libtorrent's deadline picker: send the next few seconds to the peer with the lowest estimated queue time ([libtorrent streaming](https://www.libtorrent.org/streaming.html)), and hedge only the first post-seek range.

## Transcoding belongs to one GPU per session, placed anywhere in the house

Spawn a **pinned jellyfin-ffmpeg** build as a supervised subprocess, one per session. Generate its argv from typed models: (source facts from the scan DB) × (node capability) × (client profile). jellyfin-ffmpeg carries **98 patches** that stock FFmpeg lacks. One example: stock ffmpeg silently ignores the `p`/`u` pause and resume keys used for throttling. A crashed subprocess can't take down the server ([jellyfin-anemone RESEARCH.md](https://github.com/calibrae/jellyfin-anemone/blob/main/RESEARCH.md)). Jellyfin says builds from elsewhere give "partial acceleration" ([Jellyfin HWA docs](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/)). Mangling argv between vendors has failed in every earlier project, so regenerate argv per node ([anemone](https://github.com/calibrae/jellyfin-anemone/blob/main/RESEARCH.md)). Pass the stored probe data and small probe sizes. Jellyfin's `-analyzeduration 200M -probesize 1G` is costly on network storage.

Hardware ranking for 4K HDR→1080p SDR:

1. **Intel QSV**: no session cap ([Jellyfin Intel docs](https://jellyfin.org/docs/general/administration/hardware-acceleration/intel/)). An Iris Xe ran **3 × 4K60 HDR10 streams (218 fps total)**, about 9 films' worth at 24 fps. An Arc B580 handles ~8 HDR streams ([computingforgeeks, Oct 2026](https://computingforgeeks.com/best-gpu-jellyfin-plex-transcoding/)).
2. **Apple VideoToolbox**, tied with Intel: an entry M1 does **3 × 4K24 Dolby Vision→SDR**, and Max and Ultra chips add encode engines ([Jellyfin Apple docs](https://jellyfin.org/docs/general/post-install/transcoding/hardware-acceleration/apple)).
3. **NVIDIA**: an RTX 3060 runs ~11 streams, but GeForce cards are capped at **12 encode sessions per host** (8 in older SDK docs) ([NVIDIA SDK 13.1](https://docs.nvidia.com/video-technologies/video-codec-sdk/13.1/nvenc-application-note/index.html)).
4. **RK3588**: 4K HEVC 10-bit → H.264 at **311 fps** on one stream ([Turing Pi](https://turingpi.com/jellyfin-rk3588-hardware-transcoding-turing-pi-arm64)).
5. **AMD via VA-API**: check tone mapping on each GPU generation.

An N100 manages about 2 HDR streams. The scheduler should advertise **a measured fps budget, not a session count**.

Tone mapping is the expensive step. On CPU it takes a Ryzen 9 5950X to keep up with one 4K60 DV stream ([Jellyfin hardware selection](https://jellyfin.org/docs/general/administration/hardware-selection)). The pipeline rule is zero-copy HW decode, then **scale to 1080p before tone mapping** (a quarter of the pixels), then HW encode. A benchmark that tone-mapped at 4K first cut an Arc A380 from 9 streams to 3 ([computingforgeeks](https://computingforgeeks.com/best-gpu-jellyfin-plex-transcoding/)). Use fixed-function VPP or VideoToolbox-native tone mapping for HDR10/HLG, since they draw less power. Use OpenCL, CUDA, Metal or libplacebo for DV Profile 5, which has no fallback layer. Tag P5 at scan time so those jobs only go to capable nodes. For output, prefer HW HEVC (**~30% fewer bits than x264**) and HW AV1 (**~40% fewer**) where the client decodes it, with H.264 as the universal fallback ([Fora Soft](https://www.forasoft.com/learn/video-quality/articles-vqm/encoder-comparison-x264-x265-svt-av1)). HW encoders cost 1–4 VMAF points against good software encodes.

Distribute by **session, not by chunk**. Real-time playback needs only 1×. Splitting one live stream across machines was rejected twice upstream because of VRAM duplication and keyframe artifacts ([anemone](https://github.com/calibrae/jellyfin-anemone/blob/main/RESEARCH.md)). The node serving the client owns the session and its playlist. It picks a transcode node by fps headroom, capability and network path to the media. That node reads the source directly over an iroh range stream and pushes fMP4 segments back with checksums: ffmpeg never reads the HTTP status of its own PUTs. Use fixed segment boundaries (segment N = [N·d, (N+1)·d) with forced keyframes every 2–4 s). Then a seek, failover or migration is just a restart at `-ss N·d -start_number N` on any node. Throttle by pausing at about 60–180 s ahead; Jellyfin's default is 180 s ([jellyfin#16608](https://github.com/jellyfin/jellyfin/issues/16608)). This removes the shared-NFS requirement that breaks rffmpeg (15–60 s segment lag) and ClusterPlex.

Many transcodes can be avoided altogether. Audio-only direct stream runs 10–58× real time on a modest CPU ([jellyfin#16608](https://github.com/jellyfin/jellyfin/issues/16608)). Pre-generating an EAC3/AAC companion track for every TrueHD/DTS title at scan time (~0.29 GB/hour at 640 kbps) removes most audio jobs. PGS subtitles force a full video burn-in on clients that can't render them ([jellywatch](https://jellywatch.app/blog/jellyfin-direct-play-vs-transcoding-explained-2026)). Render them on the client, OCR them to text at scan time, or burn in with a HW overlay. Use idle GPUs overnight for **chunk-split pre-transcodes** of titles that remote or incompatible clients actually play. Splitting at keyframes is safe for offline work, with audio muxed once at the end ([rustyguts](https://rustyguts.dev/posts/basics-of-chunked-video-coding)).

## A Navidrome-style scanner keeps 100k files under a cheap rescan

Jellyfin and Plex scans are heavy because small changes escalate. In Jellyfin 10.11, one new subtitle in a movie folder triggers a scan of the whole library root, followed by fresh `ffprobe -probesize 1G` runs ([jellyfin#13401](https://github.com/jellyfin/jellyfin/issues/13401)). One full scan regressed from 2.5 to 30 minutes ([jellyfin#15070](https://github.com/jellyfin/jellyfin/issues/15070)). Jellyfin once launched 1,105 concurrent ffprobes ([jellyfin#14497](https://github.com/jellyfin/jellyfin/issues/14497)).

Navidrome shows how to keep scans light. Each folder row stores a hash over the sorted file names, sizes and mtimes, so an unchanged folder costs a `readdir` and `stat` calls and nothing else ([navidrome PR #4220](https://github.com/navidrome/navidrome/pull/4220)). Pair that with the `notify` crate for local disks. inotify costs ~1.3 KB of kernel memory per directory watch, and kernels 5.11+ allow up to 1,048,576 watches ([LKML](https://lkml.rescloud.iu.edu/2011.1/00435.html)). NFS and SMB mounts emit no events ([docs.rs notify](https://docs.rs/notify/latest/notify)), so the periodic hash walk is the only reliable method there. Resolve every event to the smallest affected directory. Parallelize per disk, not per core.

Probe in-process from headers. A ffprobe header check costs ~100 ms per file ([McGarrah](https://mcgarrah.org/jellyfin-media-integrity-architecture-design/)), about 2.8 CPU-hours for 100k files. The local benchmark found the MKV `Cues` for 600 keyframes was **13 KB, found via the SeekHead in the first 4 KB, and read in 0.28 ms**. A full ffprobe packet scan of the same file took 394 ms. Jellyfin's own Matroska keyframe extractor is "pretty fast" next to ffprobe ([PR #6600](https://github.com/jellyfin/jellyfin/pull/6600)). From each file, store:

1. The keyframe index (pts, offset).
2. Codec-private data and a pre-built fMP4 init segment.
3. HDR/DV profile, exact frame rate and Atmos/DTS:X flags.
4. A flag for files without Cues or with `moov` at the end. These get a low-priority packet scan or the remux path; non-faststart MP4s break ExoPlayer progressive playback ([NuvioTV#3100](https://github.com/NuvioMedia/NuvioTV/issues/3100)).

Identify files by **OSHash**: size plus the first and last 64 KB, **128 KB read regardless of file size** ([opensubtitles/oshash](https://github.com/opensubtitles/oshash)). It doubles as the OpenSubtitles lookup key and the household dedupe key. Compute full BLAKE3 lazily, and only for files that will move between nodes. Hashing is disk-bound, not CPU-bound: BLAKE3 runs at 2.4–13 GB/s per core ([turboblake](https://gunta.github.io/BLAKE3-bend/benchmarks/); [daily.dev](https://daily.dev/posts/blake3-at-13gb-s-on-zen-5-pwusg1h2t)), while a NAS HDD streams 180–285 MB/s ([IronWolf Pro datasheet](https://www.asipartner.com/marketing/Seagate26/STX-disiti-32tb-LP/resources/ironwolf-pro-32-tb-DS2129-7-2510US-en_US.pdf)). Hashing 50 TB eagerly would take days.

Parse filenames offline with `hunch`, a Rust guessit port that extracts 49 properties ([docs.rs](https://docs.rs/hunch/2.0.3/hunch/index.html)). Match on TMDB, which allows roughly 40–50 requests/s and **forbids caching longer than 6 months** ([TMDB rate limits](https://developer.themoviedb.org/docs/rate-limiting); [terms](https://www.themoviedb.org/api-terms-of-use)). Fetch metadata once per household and replicate it by TMDB ID. Store artwork at one or two sizes as WebP. Skip chapter images by default: one Plex install reached 500+ GB of them ([Plex forum](https://forums.plex.tv/t/why-is-my-plex-media-server-directory-so-large/725768)).

Use **SQLite in WAL mode with `synchronous=NORMAL`, `mmap_size`, one writer task batching ~1,000 rows, and a pool of readers**. WAL+NORMAL ran 83,401 single-row transactions/s against 3,662 with FULL, and mmap added 27% to random reads ([ZeroExp](https://zeroexp.dev/library/sqlite-pragmas-web-app)). Jellyfin's "database is locked" failures came from "thousands of parallel write requests", not from SQLite itself ([Jellyfin blog](https://jellyfin.org/posts/SQLite-locking)). Keep the replicated logs in redb, as Deadbolt already does ([AGENTS.md](~/dev/deadbolt/AGENTS.md)). redb was fastest for individual writes in its author's benchmark, at 920 ms vs SQLite's 7,040 ms ([redb README](https://raw.githubusercontent.com/cberner/redb/master/README.md)). For search, nucleo matches 95k titles in **7.4 ms** per keystroke ([fuzzy-benches](https://github.com/noib3/fuzzy-benches/)), and FTS5 handles overview text. tantivy isn't needed at this scale.

For a baseline, Navidrome claims under 50 MB RAM for 29k songs ([Docker Hub](https://hub.docker.com/r/deluan/navidrome)). Ferrofin idles at 154 MiB against Jellyfin's 393 MiB ([Ferrofin](https://github.com/mangoleaf/ferrofin)). A target of tens of MB idle for a 100k-file catalog is plausible but unmeasured.

## Three sync streams replace one log that would drown in progress ticks

Deadbolt's session is `HEADS → ENTRY* DONE → RESULT` on one QUIC stream. Membership entries go first, and the log is never compacted ([sync.rs](~/dev/deadbolt/crates/net/src/sync.rs); [design.md](~/dev/deadbolt/docs/design.md)). Heads exchange is optimal while the history is small. Watch progress breaks that assumption. Plex and Jellyfin report every **10 s** plus on every state change ([Plex developer docs](https://developer.plex.tv/pms); [jellyfin-web playbackmanager.js](https://raw.githubusercontent.com/jellyfin/jellyfin-web/master/src/components/playback/playbackmanager.js)). At 3 hours a day that is ~1,080 signed ops per viewer per day, every one of which a device returning after weeks offline would replay. The fix is to split state by write pattern into three streams.

**Membership and grants** stay exactly as Deadbolt does them: a signed causal Add/Remove log, synced first, never pruned, gated on both accept and dial. Pairing works the same way. The new device shows a QR code with its public key, a one-time secret and a relay hint. An existing device scans it and both confirm a 6-digit code ([design.md](~/dev/deadbolt/docs/design.md)). This fits TVs well: the TV, which can't scan, displays the code, and a phone scans it. Friends get `Grant{friend_key, library, read, expires}` and `RevokeGrant` ops in the same log. The serving server checks the grant with an O(1) set lookup per request. A UCAN, Biscuit or Meadowcap chain would cost one signature check per delegation hop, with revocation lists bounded only by expiry ([UCAN revocation](https://github.com/ucan-wg/revocation/blob/main/README.md); [Biscuit](https://www.biscuitsec.org/docs/guides/revocation)). Bearer capabilities with short expiries are only needed if a friend's server re-serves cached content. Friends' progress lives in their own stream and is shared back.

**The catalog** has a single writer, the server that owns the files. Replicate it as a per-server sequence feed ("changes since N"): one round trip and an 8–16 byte cursor. Use **negentropy range-based set reconciliation** as the fallback when a peer's cursor is older than the tombstone horizon, and as periodic anti-entropy between servers. RBSR needs about **log₁₆(n)/2 round trips: ~3 for a million items**, regardless of how many items differ, and needs no shared history ([Hoyte, RBSR](https://logperiodic.com/rbsr.html)). Nostr relays sync tens of millions of elements this way, and a Rust crate exists ([negentropy](https://github.com/hoytech/negentropy)). Partial sync by key prefix also covers "only the libraries this friend was granted".

**Watch progress** becomes an LWW register per (user, item), ordered by a hybrid logical clock with the device ID as tie-breaker. Willow shows the pruning semantics: a newer entry deletes older ones under the same key ([Willow data model](https://willowprotocol.org/specs/data-model/index.html)). Coalesce in three tiers. A 1 Hz "now playing" stream is ephemeral and unsigned. A 10 s local write gives crash safety. A signed replicated op is emitted only on start, pause, stop, a seek over 30 s, crossing the watched threshold, and a 2–5 min heartbeat. That is about **40–100 ops a day instead of 1,080**, batch-signed. Keep "played" as a separate register so a stale position can't un-watch an item. Bound each device's log with a signed `Checkpoint{covers, state_root, prune_below}`, following p2panda's `PruneFlag` ([p2panda prune](https://docs.rs/p2panda-core/0.7.1/p2panda_core/prune/index.html)). A peer behind the floor receives state via RBSR instead of ops. Loro documents the same trade-off for shallow snapshots ([Loro](https://loro.dev/docs/concepts/shallow_snapshots)). Automerge, Loro and yrs bring per-op history that single-writer records don't need.

Topology stays simple. Clients connect to one or two household servers, and servers form a full mesh. New heads go out as an eager `NOTIFY` over open connections; heads exchange runs on reconnect. iroh-gossip's default active view is 5 peers ([iroh-gossip](https://docs.rs/iroh-gossip/0.101.0/iroh_gossip/proto/index.html)), so it adds nothing for a household and should carry only wide ephemeral traffic such as now-playing. Deadbolt's deterministic simulator ([simulation.md](~/dev/deadbolt/docs/simulation.md)) can be extended with four checks: LWW convergence after a prune, catch-up from behind the prune floor, a revoke stopping catalog flow within one round, and bounded catch-up bytes after a four-week partition.

## Jellyfin's API buys a client ecosystem; only a native client gets the mesh

The client ecosystem is the shortcut. Ranked by direct-play breadth, the clients are: Infuse on Apple; Kodi and mpv-based apps (Swiftfin-MPV, Streamyfin, Findroid, Jellyfin Media Player); Jellyfin Android TV with FFmpeg audio; the TV-native apps; AVPlayer-only apps; and browsers last ([Swiftfin players.md](https://github.com/jellyfin/Swiftfin/blob/main/Documentation/players.md); [Jellyfin codec support](https://jellyfin.org/docs/general/clients/codec-support)). All of them speak the Jellyfin API. Jellyfin 12.0 (7 Sep 2026) **removed `/emby` and `/mediabrowser` routes and disabled legacy auth**, which narrows what a compatible server must emulate ([Jellyfin 12.0](https://jellyfin.org/posts/jellyfin-release-12.0/)). A video-only subset of roughly 30–50 operations covers auth, views, items, resume, Next Up, PlaybackInfo, stream/HLS, images, sessions/progress and media segments. Ferrofin shows full coverage is reachable: all 412 operations wired, in Rust. It also shows parity is the hard part, with only 7 of 412 operations deep-verified ([Ferrofin FEATURES.md](https://github.com/mangoleaf/ferrofin/blob/main/docs/FEATURES.md)). Ferrofin is GPL-3.0, so implement the API from the OpenAPI spec rather than copying its code. Answer DeviceProfile/PlaybackInfo honestly, because clients such as Jellyfin Android TV 0.19 now decide transcodes from it ([jellyfin-androidtv#5073](https://github.com/jellyfin/jellyfin-androidtv/issues/5073)). Jellyfin's founding leadership left in July 2026 ([Linuxiac](https://linuxiac.com/jellyfin-loses-project-leader-and-core-team-member-in-major-shake-up/)), so the API's future direction carries some risk.

Third-party apps speak HTTP to a single address. They can't dial iroh keys, hole-punch or fetch from several sources. Through the facade they reach the merged household catalog on the LAN, or remotely through a forwarded port or relay ingress. The native client is where the design's advantages show up. A Rust core embeds iroh, pre-dials every server, runs the deadline-aware range fetcher, and exposes a **loopback HTTP endpoint**. AVPlayer or ExoPlayer read from it first, for power efficiency, AirPlay and frame-rate matching, with libmpv/MPVKit as the fallback for everything else. Swiftfin users explicitly ask for that order ([Swiftfin#1853](https://github.com/jellyfin/Swiftfin/issues/1853)). Frame-rate and dynamic-range matching are features each app must opt into: AVDisplayManager on tvOS, `setFrameRate()` on Android ([Android frame rate](https://developer.android.com/media/optimize/performance/frame-rate)). Streamyfin's Apple TV build never switches refresh rate ([Streamyfin#2261](https://github.com/streamyfin/streamyfin/issues/2261)). The server must report exact frame rate and DV profile before playback starts.

Aim transcodes and pre-transcodes at one universal profile: H.264 or HEVC Main10 in fMP4, AAC stereo plus E-AC3 5.1, DV P8.1/P5 or HDR10, and WebVTT sidecars. It plays on Safari/AVPlayer, Roku, webOS, Tizen and Android TV. For DV Profile 7, send the file unchanged and let capable clients fall back to the HDR10 base layer, as Plex does on Shield ([jellyfin-androidtv#5303](https://github.com/jellyfin/jellyfin-androidtv/issues/5303)). The web client can demux MKV itself with **Mediabunny** (~30 kB gzipped, pure TypeScript on WebCodecs) and feed fMP4 into MSE or ManagedMediaSource ([mediabunny.dev](https://mediabunny.dev/)). The server then serves byte ranges and transcodes only audio that browsers can't decode: DTS in any browser, AC-3 in Chrome and Firefox.

## One fused pass per file buys every playback nicety for under a CPU-minute an hour

The industry has converged on **typed time-range markers stored by the server and acted on by the client**. Implementing Jellyfin's Media Segments shape (Intro, Outro, Recap, Preview, Commercial) lights up skip buttons in existing Jellyfin clients and Infuse with no client work ([Jellyfin media segments](https://jellyfin.org/docs/general/server/metadata/media-segments/)). Fill segments in order of cost:

1. Chapter names, which are free.
2. TheIntroDB, keyed by TVDB ID (anonymous: 30 requests/10 s and 5,000 lookups/day; with a key: 100,000/day; [TheIntroDB](https://github.com/TheIntroDB/jellyfin-plugin)), or IntroDB, which needs no key ([introdb.app](https://introdb.app/)). Verify locally: community timestamps can belong to a different release of the same episode ([Firecore community](https://community.firecore.com/t/infuse-using-both-the-intro-database-and-jellyfin-intro-skipper-markers-when-timestamps-differ/60000)).
3. Chromaprint across a season's episodes, over only min(25% of runtime, 10 min) ([intro-skipper wiki](https://github.com/intro-skipper/intro-skipper/wiki/Settings-%E2%80%90-Analysis)).
4. Keyframe-only black-frame scans for credits in the final 15 minutes.

Emit nothing at low confidence: "a missing skip button is better than one that skips into the story" ([Media Preview Generator](https://github.com/stevezau/media_preview_generator/blob/dev/docs/skip-intro-credits.md)). Use the credits start, not a percentage, to trigger Up Next and mark an item watched, as Plex does.

Each feature is cheap on its own. Keyframe-only trickplay is **~110× faster** than full decode (244 vs 2.2 fps, [jellyfin#11336](https://github.com/jellyfin/jellyfin/issues/11336)). The local benchmark measured **~9 CPU-s and ~2.9 MB per hour** of 720p at 320 px every 10 s, against Plex's 10–50 MB BIF per item ([Plex Support](https://support.plex.tv/articles/202197528-video-preview-thumbnails/)). QSV and CUVID can't skip non-keyframes, so software keyframe decode beats GPU decode here. EBU R128 loudness took ~4.4 CPU-s per hour of stereo audio in the same benchmark. Plex's Normalize Loudness and Boost Dialog **force a server audio transcode** ([Plex Support](https://support.plex.tv/articles/audio-track-enhancements-for-video/)). Storing a few floats per track and applying gain and compression on the client keeps direct play intact.

Subtitles follow the same tiered logic:

1. Text tracks already in the file.
2. OpenSubtitles by moviehash. Exact-hash matches need no sync, but the free tier allows only 5–20 downloads a day, so run one household-wide quota manager and share every result ([OpenSubtitles](https://opensubtitles.tawk.help/article/about-the-api)).
3. alass, a Rust subtitle syncer: ~15–30 s per film, with 90% of lines landing within 400 ms ([alass](https://github.com/kaegi/alass)).
4. OCR of PGS subtitles with RapidOCR.
5. Generated subtitles. Use Parakeet TDT v3 on Apple Silicon, where an hour takes ~23–60 s ([MacParakeet](https://macparakeet.com/blog/whisper-to-parakeet-neural-engine/)), or Whisper large-v3-turbo at 35× real time on an RTX 4090 ([Runpod](https://www.runpod.io/articles/guides/best-gpu-for-whisper)). Never run this on a NAS CPU.

For Live TV, record HDHomeRun MPEG-TS untouched at about 6 GB/hour ([SiliconDust](http://info.hdhomerun.com/info/dvr)). Run comskip at 2–5 minutes per recorded hour ([Channels community](https://community.getchannels.com/t/how-many-cores-for-comskip-with-4-available/26047)) and store commercials as `Commercial` segments.

The per-feature costs matter less than how the work is scheduled. Excluding speech-to-text and DVR, every analyzer together costs about one CPU-minute per hour of video, and the bottleneck is **reading the file**. So fuse the analyzers into one demux pass: video keyframes feed tiles and black frames, and audio feeds R128, the Chromaprint windows and the speech-activity timeline that later sync runs reuse. Key every result by `(content_id, analyzer, version, params_hash)`. Replicate small results through the metadata log and fetch large blobs, such as tiles and subtitles, on demand. Claim jobs with replicated leases. Place them on the node that holds the file, then on idle, AC-powered nodes, then by capability (GPU or Neural Engine for speech-to-text). This is Plex's hash-keyed cloud marker cache ([Plex Support](https://support.plex.tv/articles/credits-detection/)) without the cloud. No current server schedules across household nodes this way. Media Preview Generator's worker groups come closest ([MPG](https://github.com/stevezau/media_preview_generator/blob/dev/README.md)). The other server-side features to build are SyncPlay-compatible group playback, which users miss now that Plex removed Watch Together, plus per-user, per-series track preferences, versions with version-aware resume, and profiles with parental ratings.

## Conclusion: build order for the first slices

Raw speed isn't the main gap between this design and Plex. Any tuned stack fills a home link. The gap is where the waiting happens: relay caps, process restarts on seek, multi-request start handshakes, whole-library rescans, and logs that keep every 10 s tick. Every layer above removes a wait rather than speeding up a computation. The open risks have numbers attached and can be measured early:

1. iroh 1.3's real throughput with BBR on Linux.
2. Relay-to-direct upgrade time.
3. A pure-Rust MKV reader's coverage of real-world files.
4. How much of the Jellyfin API surface Infuse actually requires.

The build order front-loads exactly those measurements.

| # | Slice | Done when |
|---|---|---|
| 1 | **Transport benchmark and tuning.** Reuse Deadbolt's `net` crate. Add the tuned `QuicTransportConfig` (16–32 MiB / 64 MiB windows, BBR via pinned noq-proto, 2–4 range streams) and an embedded `iroh-relay` with raised per-client limits. | iroh's `transfer` example reaches ≥80% of iperf3 on a Linux LAN. A forced-relay path carries ≥100 Mbit/s. Relay→direct upgrade time is logged. |
| 2 | **Scanner and index.** Folder-hash rescans plus `notify`, in-process MKV/MP4 header parse (keyframe index, codec-private, HDR/DV, init segment), OSHash, `hunch` + TMDB, SQLite with one writer. | A no-change rescan of 100k files opens no media files. Cues-based indexing covers most of the test library. |
| 3 | **Household identity and direct play.** Deadbolt membership log and QR pairing for servers and clients. A range-read ALPN over iroh. A native desktop client (Rust core, loopback HTTP, libmpv) that pre-dials and plays one-round-trip `/play` responses. | Warm seek reaches first byte in <60 ms at 30 ms RTT. Start on the LAN is under ~300 ms. |
| 4 | **Three-stream sync.** Per-server catalog feeds into a merged household view. LWW progress registers with HLC, coalescing and checkpoints. Negentropy fallback. Simulator properties for prune, revoke and a 4-week partition. | Two servers and three clients converge. Catch-up bytes after a simulated 4-week partition stay bounded. |
| 5 | **Jellyfin 12 facade and in-process HLS.** About 30–50 operations including PlaybackInfo, MediaSegments and sessions, plus a stateless fMP4 remux from the index. | Infuse, Swiftfin, Jellyfin Android TV and jellyfin-web browse the merged catalog and direct play or remux without any ffmpeg process. |
| 6 | **Distributed transcoding.** jellyfin-ffmpeg supervisor, argv compiler, fps-budget capability registry, per-session placement on any node, fixed segment timeline, checksummed segment push, EAC3/AAC companion tracks. | A 4K DV P5 title plays on an AVPlayer client while transcoded on a different node. Failover restarts at a segment index. |
| 7 | **Fused analysis pass.** Trickplay tiles, R128, chapter→segment mapping, TheIntroDB/IntroDB lookup, Chromaprint and black-frame credits, keyed by content hash, replicated, with leased jobs. | Skip buttons and trickplay appear in Jellyfin clients. Each file is read once. |
| 8 | **Sharing and extras.** Friend grants, SyncPlay, offline downloads via iroh-blobs multi-source, subtitle download/sync/OCR/STT, HDHomeRun DVR with commercial segments. | A friend outside the household streams a granted library over a home relay, and revocation cuts them off within one sync round. |
